## 1. Platform verdict — we need Linux x64, and there are two independent reasons

**Recommendation: move benchmarking to a Linux x64 host. Exec action item #9.**

The two reasons are orthogonal. Either one alone justifies the move; together they make continuing
on this hardware indefensible.

### Reason 1 — RocketRide cannot be containerised on Apple Silicon at all [VERIFIED]

`server-v3.3.1` ships exactly three assets:

| asset | runs on this host? |
| --- | --- |
| `rocketride-server-v3.3.1-darwin-arm64.tar.gz` | natively, **but not in a Linux container** — the binary is Mach-O |
| `rocketride-server-v3.3.1-linux-x64.tar.gz` | **only under x86 emulation** |
| `rocketride-server-v3.3.1-win64.zip` | no |

**There is no `linux-arm64` build — and there never has been.** All **51 published releases** were
examined: 36 carry `win64`, 24 `darwin-arm64`, 24 `linux-x64`, and **zero** carry `linux-arm64` or
`linux-aarch64`. The project's own Docker workflow targets `linux/amd64` only. So on this machine the choice is: run RocketRide natively while LlamaIndex is containerised
(asymmetric — worse than no containers), or emulate x86 (which `DOCKER_ARCHITECTURE.md` §1 forbids
because emulation silently changes every number and looks like a framework difference).

**On a Linux x64 host the shipped build runs natively and both arms containerise symmetrically.**
The blocker disappears entirely — it is a platform property, not something better engineering fixes.

## 2. What was actually measured — functional equivalence, established

**The strongest result in this project: under a matched configuration the two arms are
functionally identical except for one defect.**

Three blocks per arm, 2,000 documents each, interleaved in one session, both arms verified at
10 intra-op threads *inside the process* before the run began:

| arm | goodput (3 blocks) | faults (3 blocks) | content-suspect (3 blocks) |
| --- | --- | --- | --- |
| LlamaIndex | **1,972 · 1,972 · 1,972** | 28 · 28 · 28 | 23 · 23 · 23 |
| RocketRide | **1,965 · 1,965 · 1,965** | 35 · 35 · 35 | 23 · 23 · 23 |

**Identical to the document, every block, both arms. [VERIFIED — 3/3 reproduction]**

**The two arms differ by exactly 7 documents per 2,000 (0.35 %), and every one of them is the NUL
truncation of §3.1.** Same corpus, same order, same chunking, same model, same thread count: the

> **This is the finding to lead with.** It says the two implementations do the same work and get
> the same answer — which is what "service parity" was supposed to establish — and it isolates the
> single behavioural difference to a specific, filed, reproducible bug rather than a diffuse
> quality gap.

> *Hostile reviewer: "Identical counts three times running — is the harness just replaying a cached
> result?"* Each block constructs a fresh arm (a new RocketRide task, a new LlamaIndex process),
> re-extracts every PDF from disk, and re-embeds. The determinism is the corpus and the pipelines
> being deterministic, which is the claim. The RSS series differ block to block (§4), so the blocks
> are demonstrably not identical executions.

## 3. Three product findings — our benchmark found these before a customer did

### 3.1 NUL truncation: silent data loss in the response path [VERIFIED]

**Minimal reproducer, no PDF:**

```python
send(token, "AAAA\x00BBBB")   →   page_content == "AAAA"
```

Everything from the first NUL onward is discarded from the returned text.

**The embedding is correct.** cos(returned vector, embedding of the **full** text) = **1.0000**;
against the truncated text, 0.7698. The engine embedded everything and lost it only on the way out.

| aspect | finding |
| --- | --- |
| scope | **only `0x00`** — all 32 other control chars (`0x01`–`0x1F`, `0x7F`) return intact |
| fields | only `page_content`; `embedding`, `metadata`, `embedding_model`, `type` intact |
| boundary | always cut at the **first** NUL; a leading NUL empties the chunk entirely |
| prevalence | **0.30 % of documents [VERIFIED, 2 methods]** — offline scan 3/991; live pipeline detection 8/2,200 = 0.36 %, inside that CI. ≈ **30 documents per 10,000** |

**Impact:** a RAG system retrieves the right chunks and displays truncated or empty text. It is
silent — the vectors look perfect. One affected document with a *clean-looking* printable ratio of
0.992 loses **98.9 %** of its text, so no content heuristic protects a consumer from this.

Filing-ready report with version/build identity, boundary matrix and maintainer objections
answered: **`publishable/BUG_NUL_TRUNCATION.md`**.

### 3.2 Thread configuration: 19 % throughput and most of concurrency scaling, with no config surface [VERIFIED]

The engine's node processes let native math libraries size their own thread pools. Under
concurrency those threads oversubscribe the machine.

| | scaling, concurrency 1→32 |
| --- | ---: |
| default | **1.43×** (400 tok) / 1.18× (1,600 tok) |
| thread-pinned | **3.04×** / 3.05× |

Pinning roughly **doubles concurrency scaling** and adds ~19 % throughput at concurrency 8 — but
**costs 41–45 % at concurrency 1** on the 400/1,600-token synthetic text used for that
measurement, so the best setting is workload-dependent. **On the heavier GovDocs corpus the
concurrency-1 cost is larger — 3.07× (§8)** — which is the figure to use for anything involving
this corpus.

**The product gap:** the only lever is a process-level environment variable at engine start, global
to every pipeline on that engine. There is **no per-pipeline configuration surface**, so a
multi-tenant deployment cannot give two pipelines different settings. Verified inside the task
process (`torch.get_num_threads()` = 10 default, 1 pinned), not inferred from the flag.

**Recommendation: expose thread limits as pipeline configuration.**

### 3.3 The ~150-concurrent-pipeline livelock [VERIFIED, reproduced twice]

Creating N concurrent pipelines (one task process each) livelocks at roughly 150, leaving orphaned
`node.py` processes behind. The alternative model — N concurrent sends through **one** pipeline —
shows no process growth and no livelock.

**Impact:** the failure mode is a hang, not an error, so a client sees a timeout with no diagnostic.
**Recommendation:** document the supported concurrency model explicitly, and fail fast with a clear
error at the limit rather than livelocking.

>

>

> comparable with the counts below.

> ### ⚠️ TOPOLOGY-CONFOUNDED — see [`MATCHED_LAYERS.md`](MATCHED_LAYERS.md)
> **The two arms did not run the same shape.** LlamaIndex ran **in-process** (1 process, no
> HTTP, no serialization; `working/ws1/service.py` was never used) while RocketRide ran its
> full client→WebSocket+DAP→engine→task-tree path (3 processes). RocketRide therefore carries
> a ~240 MB engine parent with **no counterpart in the other arm**, plus two extra interpreter
> baselines and per-document serialization.
> **Direction: biases AGAINST RocketRide.** The number below is not withdrawn and is correct
> as measured — but it is a property of the topology, not of the frameworks.
> The same repo also reports LlamaIndex at **4,642 MB idle vs RocketRide 204 MB** when
> LlamaIndex is run behind uvicorn with 8 workers — **the opposite verdict on the same two
> systems.** Neither ratio is a framework property. Re-run design: `MATCHED_LAYERS.md` §3.


### The ratio [direction VERIFIED, magnitude PROVISIONAL]

Matched windows, both arms native, post-warm-up, engine resolved **by PID** (excluding 104 MB of an
unrelated engine that name-matching had been counting):

| window | LlamaIndex median | RocketRide median | ratio |
| --- | ---: | ---: | ---: |
| documents 0–267 | 938 MB | 1,954 MB | **2.08×** |
| documents 0–2,100 | 972 MB | 2,018 MB | **2.08×** |
| documents 0–10,000 (both arms complete) | 1,074 MB | 2,297 MB | **2.14×** |

**Identical at both windows despite 7.9× more coverage.** Across three independent RocketRide runs
the ratio spans **1.74×–2.55×**. Quote the direction and the range; never a single decimal.

> **Are the two arms' memory even comparable?** RocketRide's figure spans a driver process *plus*
> an out-of-process engine and its task process; LlamaIndex's is one process holding one model.
> That is a real deployment difference, not an accounting error — we count everything each arm
> needs to do the work. But it does mean the ratio would move with worker count on either side, so
> this is **not** a per-document memory-efficiency figure and must not be quoted as one.
>
> **Why §2's peak figures give a bigger ratio (3,791 / 1,250 = 3.03×) than the 2.08× here.**
> They are different statistics, and the difference is itself the finding. A *peak* is a single
> sample; RocketRide's peak sits 1.65× above its own median while LlamaIndex's sits 1.16× above
> its own, so comparing peaks compounds the two arms' different headroom on top of the underlying
> gap. **2.08–2.14× (median-to-median, matched windows) is the memory-consumption ratio; 3.03×
> (peak-to-peak) is what you must provision for.** Both are real; they answer different questions.

### The oscillation, and what it is not

RocketRide's resident memory swings with an amplitude ~8× LlamaIndex's. **Two exonerating
hypotheses were tested and both refuted:**

| hypothesis | test | result |
| --- | --- | --- |
| process-per-task makes spawn/exit a memory event → sawtooth is architectural | sampled the engine tree every 0.5 s for 120 s during a live run | **REFUTED** — process count **constant at 2**, one child PID throughout, while RSS still swung 488 MB |
| large documents drive transient allocations | correlated RSS against the size of the document in flight | **REFUTED** — RocketRide corr = **−0.14** (none). LlamaIndex has a *stronger* size correlation (−0.52) yet oscillates far less on the **identical** documents |

**Mechanism: UNVERIFIED.** Both leading explanations are eliminated; the remaining candidate is
allocator behaviour inside the engine's task process, which we cannot inspect from outside.

### What this means operationally — the actionable statement

**Size containers to peak, not median.** The gap is 5× larger for RocketRide:

| arm | median | p95 | observed peak | peak/median |
| --- | ---: | ---: | ---: | ---: |
| LlamaIndex | 1,074 MB | 1,119 MB | 1,250 MB | **1.16×** |
| RocketRide | 2,297 MB | 2,645 MB | 3,791 MB | **1.65×** |

A container sized to RocketRide's median would be undersized by **65 %**; for LlamaIndex, 16 %.
This is a **provisioning-headroom** statement, not a verdict on stability.

**Separately: a 42 % run-to-run spread on byte-identical input [UNVERIFIED cause].** Three
RocketRide runs over the same first 200 documents gave medians of 2,397 / 1,639 / 1,811 MB. It is
**not** explained by the sawtooth: the divergence is present in the *first* post-warm-up sample
(2,631 vs 1,949 vs 1,951), so it is set at task creation rather than accumulated. All three used
the same engine process, so it is not a fresh-engine effect. **We cannot currently explain it, and
it is the reason the memory magnitude stays PROVISIONAL.**

## 6. Roadmap

**Phase 2 — Linux x64 head-to-head.**
*Entry:* a Linux x64 host with ≥ 16 cores and ≥ 64 GB. *Exit:* both arms containerised
symmetrically, identical cgroup contracts, n ≥ 3 per cell, every cell passing a 10 % variance gate,
throughput quotable for the first time.

**Phase 3 — Multi-stage RAG.** Split + embed + index + retrieve + rerank. *Entry:* Phase 2 exit.
*Exit:* the same protocol applied to a pipeline with real inter-stage dataflow.

**Phase 4 — Agentic, LLM stubbed.** Multi-step tool-calling with a deterministic stub in place of
the model, so the orchestration is measured rather than the model's latency.

**Phase 5 — Production economics.** Cost per million documents at each arm's own operating point,
including the operational toil already catalogued.

### Why the current workload is the hardest case for RocketRide

**Single-step split+embed is the minimum possible work per request.** The engine pays a fixed
per-request cost — WebSocket, protocol, task dispatch — that is amortised over whatever work the
request does. Our earlier crossover analysis showed the ratio moving in RocketRide's favour as work
per request grows, and this workload sits at the extreme low end.

**So today's numbers are close to the engine's worst case, and Phases 3–4 are precisely where that
prediction gets tested.** If the crossover finding holds, the engine's relative position should
improve as pipelines get deeper. That is a falsifiable prediction, not an excuse — and it is worth
stating now, before the results, so it cannot be retrofitted afterwards.


## 7. Questions you should expect, answered

These are the objections I could not dismiss, with the answer I would give. Where the honest answer
is "we don't know", it says so.

> **"You built the LlamaIndex service and it wins on memory. Why should we believe you?"**

Three checks against that: the memory instrument was found to be *over*-counting RocketRide by
104 MB and was corrected against our own arm's interest; the content-sanity reclassification is
reported for our arm too (~30 of our 9,898 "goodput" documents); and the largest single finding
this cycle — the NUL bug — was found because our gate is deliberately fatal, which cost us a
16-hour phase at 2.7 % completion before we relaxed it. `STATE.md` §5 records **7 superseded or withdrawn numbers**, with more in §§3b–3e; the
withdrawals run in both directions. Two that removed a *RocketRide-unfavourable* result:
"LlamaIndex 1.73× faster" (withdrawn — unrepresentative test document) and "RocketRide is worse at
absorbing hangs, 13.82 vs 1.95" (withdrawn — two harness bugs). Two that removed a
*RocketRide-favourable* one: the "~2,600/s engine ceiling" (it was client-bound) and a ±35 %
variance "correction" that was itself wrong. **I am not claiming the balance favours either side —
only that the corrections were applied in both directions and are individually listed.**

> **"Your content-sanity threshold of 0.90 — did you pick it so document 267 would fail?"**

It was derived before being applied: legitimate documents in a 991-document sample have p1 = 0.9944
and a second-lowest of 0.9757; the two known-garbage extractions sit at 0.679 and 0.700. 0.90 is
the midpoint of an **empty band** in the measured distribution. It flags 0 of 40 legitimate
documents. If the threshold were moved anywhere between 0.72 and 0.97 the classification would not
change.

> **"The roadmap predicts RocketRide looks better with deeper pipelines. Isn't that convenient?"**

It is convenient, which is exactly why it is written down **before** Phases 3–4 run rather than
after. It is falsifiable: if the ratio does not move in the engine's favour as work per request
grows, the crossover model is wrong and should be discarded. Stating it now means it cannot be
retrofitted to whatever the results turn out to be.

> **"The ~150-pipeline livelock — is it still present in the version you tested?"**

It was reproduced twice, with 81 orphaned `node.py` processes left behind, on this same
`3.3.1.35` build. It is a property of one concurrency model (N concurrent pipelines); the other
model (N concurrent sends through one pipeline) shows no process growth and no livelock.

> **"You say throughput is invalid here, but you quote wall-clock times in §1."**

The honest position, not a dodge. The measured durations are LlamaIndex **1.12 h** and RocketRide
**2.47 h** for the same 10,000 documents in the same order — direction: LlamaIndex roughly **2.2×**
faster in wall clock.

**We do not quote that as a throughput benchmark, for four reasons, three of which we control:**

1. **The thread configurations were not matched** — RocketRide pinned to 1 thread, LlamaIndex on
   10, at a concurrency where pinning costs RocketRide **3.07× on this corpus** (§8; §3.2's
   41–45 % was measured on lighter synthetic text). The comparison is handicapped against
   RocketRide.
2. **The runs are two days apart.** Between-session comparison is this project's documented
   worst failure mode (open item F).
3. **n = 1, no pre-warm, no randomised order** — the protocol requires n ≥ 3 with a variance gate,
   and §1 shows cold-start ordering alone moves results 2.2× on this host.
4. Even correctly run, this laptop's power-state sensitivity would make the absolute numbers
   unquotable.

**What would make it quotable:** matched thread configuration chosen per arm as its best for the
target concurrency, both arms in one interleaved session, pre-warmed, n ≥ 3, both passing a 10 %
variance gate — on a Linux x64 host. That is exactly Phase 2.

The durations are reported here for one purpose only: sizing how long a full study takes (§1).

> **"Two arms, one corpus, one machine, one run each. Where are the error bars?"**

On memory, where we make a claim, there are three RocketRide runs and the spread is reported
(1.74×–2.55×) rather than averaged away. On throughput we make no claim at all. On the NUL bug the
prevalence has two independent methods and a confidence interval. Anything with n=1 is labelled
PROVISIONAL and listed in §5.

> **"What would change your mind about the platform recommendation?"**

A published `linux-arm64` build, which would remove Reason 1 entirely. Reason 2 (power-state
sensitivity) would survive it — that one is a property of the laptop, not the software.

### Memory — DIRECTION ONLY, and the reason is itself the finding

| arm | block medians | median | spread | gate |
| --- | --- | ---: | ---: | --- |
| RocketRide | 2,065 / 2,674 / 2,717 MB | 2,674 MB | **24.0 %** | **FAIL** |
| LlamaIndex | 1,009 / 1,029 / 1,054 MB | 1,029 MB | 4.3 % | OK |

**Ratio 2.60× — DIRECTION ONLY. RocketRide fails the 10 % gate, so no point estimate is
reportable**, per the protocol.

> **On the interval, because it looks quotable and is not.** The estimator is correct — ratio of
> medians (2,674 / 1,029 = 2.598), with a bootstrap interval [1.96, 2.69]. But with n=3 that
> interval is simply the **entire attainable range** of median combinations, and the point sits at
> its top only because the RocketRide sample is left-skewed (2,065 is 609 MB below the median;
> 2,717 is 43 MB above).
>
> **The deeper problem is that no central estimate belongs on this sample at all.** A median and a
> confidence interval describe a *stationary* sample. RocketRide's is **trending**
> (2,065 → 2,674 → 2,717), which is exactly what the 24 % gate failure signalled. Report the trend,
> not a centre with a bracket.

> ### ⚠️ CORRECTION — the "+32 % monotonic growth" claim is WITHDRAWN
>
> On three blocks the RocketRide series read 2,065 → 2,674 → 2,717 MB and I called it monotonic
> growth. **Three more blocks on the same engine, never restarted, gave 2,055 → 2,070 → 2,112.**
>
> | block | 1 | 2 | 3 | 4 | 5 | 6 |
> | --- | ---: | ---: | ---: | ---: | ---: | ---: |
> | median RSS | 2,065 | 2,674 | 2,717 | **2,055** | 2,070 | 2,112 |
> | delta | — | +609 | +43 | **−662** | +15 | +42 |
>
> **It is not a leak and not a trend.** Four of six blocks cluster at **2,055–2,112 MB (2.7 %
> spread)**; blocks 2–3 were a transient excursion to ~2,700 that fully reverted. Three points
> caught the rising half of an excursion and I over-read it.

**What the six-block series actually shows:** a modal working set of ~2,070 MB with occasional
excursions of ~+30 %. The 24 % spread that fails the gate is **bimodality, not drift** — which is a
different operational statement: capacity must cover the excursion, but the service is not
degrading over time.

**Component decomposition [VERIFIED — blocks 4–6, sampled separately during each block]**, which
also corrects a reasoning gap in the earlier analysis (teardown RSS is not operating RSS, so
"engine is 192 MB after teardown" never ruled out parent growth):

| component | block 4 | block 5 | block 6 | trend |
| --- | ---: | ---: | ---: | ---: |
| engine process (parent) | 238.7 | 242.2 | 242.5 | +3.8 MB — **flat** |
| task tree (children) | 1,568.6 | 1,551.0 | 1,538.2 | −30.4 MB — **declining** |
| our driver process | 267.3 | 303.2 | 319.0 | **+51.7 MB** |

**Neither the engine nor its task is growing. The only component that grows is our own harness**,
by ~52 MB over three blocks — an instrument artifact worth ~2.5 % of RocketRide's total, and one
that **inflates** RocketRide rather than flattering it.

### ⚠️ Rule-5 inversion: the harness favours LlamaIndex here, and correcting for it moves the ratio AGAINST RocketRide

This result is unfavourable to RocketRide, so the hunt was for artifacts that unfairly **penalise**
it. One is real and material:

**The LlamaIndex arm gets a fresh process every block; the RocketRide engine persists across all
six.** LlamaIndex's memory therefore *resets* every 2,000 documents while RocketRide's does not.
Its first-sample-per-block confirms it: RocketRide 908 → 1,940 → 1,882 MB, LlamaIndex 820 → 1,032
→ 906 MB.

**But in production both services are long-running, so the reset is the unrealistic half.** That
gives two defensible numbers for two different questions:

With six blocks the picture is simpler than it looked at three, and three independent methods now
converge:

| method | ratio |
| --- | ---: |
| matched-window, 10,000-doc runs (different harness) | **2.08×** |
| fresh-vs-fresh, block 1 vs block 1 | **2.05×** |
| **all-six-block median (2,091 / 1,029)** | **2.03×** |

**RocketRide uses about 2× the memory of LlamaIndex on identical work.** [direction **VERIFIED**,
three methods; magnitude ~2.0× **PROVISIONAL** — the gate still fails at 24 % because of the
bimodality, not because the centre is uncertain.] The earlier ~2.5–2.6× reading came from the two
excursion blocks and should not be used.

**The most likely external explanation was tested and REFUTED [VERIFIED].** Retrospectively the
excursion correlated perfectly with session structure — it occurred in exactly the 2 RocketRide
blocks that followed a LlamaIndex block, and in none of the 4 that did not (6/6). That suggested
host contamination from a neighbouring process rather than anything in the engine, which would have
exonerated RocketRide and changed the sizing guidance.

**A direct test refutes it.** RO → LL → RO in one session, same engine, never restarted:

| block | median (engine + task) |
| --- | ---: |
| RO#1, before any LlamaIndex | 1,826.0 MB |
| LlamaIndex block | 1,002.5 MB |
| **RO#2, immediately after it** | **1,819.6 MB — −0.4 %** |

**No excursion.** The retrospective 6/6 correlation was confounded by session and time-of-day, and
does not survive a controlled test. Host memory was sampled throughout this time and showed nothing
distinguishing (host used ~25.2 → 25.9 GB, swap flat at 4,957 MB).

**Mechanism of the excursion: UNVERIFIED, and now with one hypothesis eliminated.** With the parent and task both flat across blocks 4–6,
whatever produced the blocks 2–3 excursion is intermittent and not cumulative. **A18 (restart the engine between blocks) is no longer the right next experiment** — there is no
growth to reset. The neighbouring-process hypothesis is now also eliminated. Host-level sampling
has been added to the harness, so the next occurrence will be attributable; A19 remains open as
**instrumented but not yet triggered**.

**On the memory accounting, because I nearly got it wrong in RocketRide's favour.** Our driver
process grows +51.7 MB across blocks and is counted in RocketRide's total. Excluding it looked
like the obvious fix and moved the ratio **2.01× → 1.74×**. It is **asymmetric**: the LlamaIndex
figure is a single process that already contains the same harness work (pypdf, the driver loop) and
cannot have it subtracted out. Symmetric options are count-on-both (**2.01×**) or exclude-from-both
(**~2.47×**, worse for RocketRide). **The as-measured 2.01× stands, and it is the conservative
choice.** The driver series is recorded separately so its growth stays visible.

### Run cost — NOT a throughput comparison

RocketRide 14.7 min vs LlamaIndex 13.5 min per 2,000 documents (**1.09×**). Reported as run cost
only; **A13 makes throughput on this host unquotable in any configuration**, exactly as §5 states.

**The wall-clock collapse, stated precisely.** The endurance run showed a 2.2× gap; under matched
threads it is 1.09×. Three things follow, and only the first two are established:

1. **The endurance gap was substantially configuration, not framework.** [supported — the only
   variable changed was thread count, and the gap fell by ~92 % of its excess]
2. **The endurance comparison is VOID, not correctable.** The 3.07× pinning cost came from short
   blocks under different thermal and memory conditions; it must not be applied as a correction
   factor to a 2.47-hour continuous run. That comparison is discarded and replaced, not adjusted.
3. **The true direction is a Phase 2 question.** 1.09× is itself unquotable on this host (A13).
   This is **not a finding and not a reversal claim** — LlamaIndex remains nominally ahead, and
   whether that survives a properly-instrumented Linux x64 run is untested.

### The endurance comparison is void, not correctable

The 3.07× pinning cost was measured on short blocks under different thermal and memory conditions
than a 2.47-hour continuous run. **It must not be applied as a correction factor to the endurance
run's 2.47 h.** That comparison is discarded and replaced by this one, not adjusted.

### The early signal that preceded this run, and how it held up

The thread-choice measurement above is a **within-arm self-comparison**, but it is suggestive: at
concurrency 1 on this corpus, unpinned RocketRide ran at **12.102 docs/s** against unpinned
LlamaIndex at **10.673 docs/s**. **[NOT A COMPARISON — different harnesses, not interleaved
against each other, and throughput on this host is not quotable.]** It is reported only because it
points the opposite way to the endurance run's wall clock, which is consistent with that gap having
been a configuration artifact rather than a framework difference. **The replication settled it:** the gap did shrink dramatically (2.2× → 1.09×), so the signal
pointed the right way — but the replication's own run-cost figure is equally unquotable, and only
Phase 2 can turn either into a claim.
